## Problem Statement

The operator watches agents through the control plane. Two motions tell the operator that work is live: the spinner face that steps beside the written word while a ticket stands in its Starting window, and the pop that carries the Decision modal and the Live view to their settled size in 120 ms. Today those motions are painted the expensive way. Each step of the face and each step of the pop is a per-frame value held in React state, and a per-frame value in React state is a repaint: the face step re-runs the ticket list's row shaping and element tree, and the pop step re-derives the modal's frame geometry and re-wraps its body text at the intermediate width, in the detail body and in the live body facts alike. The plane is one root React screen, so a repaint is a re-layout of the region's whole element tree. Then the renderer writes a frame, and the module that owns the renderer forces a full repaint on every frame (the workaround ADR 0145 keeps until the byte-loss signal exists), so every step costs a whole screen of terminal bytes.

The machine running the plane pays this twice. Ten face steps per second are ten element-tree re-layouts and ten full-screen rewrites per second, and each pop opening is a body re-wrap on every tick. The CPU the animation steals is the CPU the observation cycle needs to settle the turns the agents end; the frame tests already record the class of flake where a loaded runner deschedules the plane's worker and the frame waits stretch (ADR 0128). The test suite pays it a third way: the animation's clock stands in a wall-clock interval inside the screen, and the test has no hand on it, so the suites wait on wall-clock graces over the animation's budget (a 250 ms sleep over the pop's 120 ms budget) or on frame-stream waits that can miss the window.

## Solution

The operator sees the same plane. The face steps beside its word at the same 100 ms step, the modal pops to its settled size in the same 120 ms with the same easing, the screen keeps painting new rows, selections, and messages while the motion runs, and the no-color presentation keeps the word and drops only the color. The machine spends each tick on the tick: the per-frame values (the face frame index, the pop scale) leave React state and stand in one shared frame module. A tick advances the module's clock, the module hands the frame's facts to the paint layer (the shared presentation resolves the face's text and the modal's frame geometry, the shared paint layer resolves the colors from the Theme the environment resolved), and the renderer paints the frame. No repaint, no element-tree re-layout, no body re-wrap. The renderer's frame loop runs only while a frame owner is active, and the module drops it when the last owner leaves, so a resting plane keeps its one-frame-per-commit economy. With the renderer adapter's repaint policy (ADR 0145) the frame the tick paints writes only the cells it changed, and the face step becomes a one-glyph change on the terminal. The test suite gains one named operation that advances the animation frame by a named amount, and the suites assert the frame they chose: the face frame at a named tick, the box size at a named tick, the settled frame at rest, the wall-clock graces retired.

## User Stories

1. As an operator watching agents, I want the spinner face to keep stepping beside its written word while a ticket stands in its Starting window, so that live work reads as live.
2. As an operator watching agents, I want the face to stand on its first frame the moment the Starting window opens, so that I see the handoff is in flight before any step has run.
3. As an operator watching agents, I want the face to leave the row the moment the window ends, so that a running or a failed start wears its own badge, never a face.
4. As an operator watching agents, I want a failure marker to beat the face in both the row and the detail header, so that a dead or blocked Agent is never hidden behind the motion.
5. As an operator watching agents, I want the Decision modal and the Live view to open with the same pop to the same settled size they do today, so that the screen feels unchanged.
6. As an operator watching agents, I want the pop to be at rest before my confirm key lands, so that I confirm on a screen that is not moving.
7. As an operator watching agents, I want the face and the pop to read the same in herdr's theme, in the plane's own theme, and in the no-color presentation (the word kept, the color dropped), so that the motion is the plane's and never the theme's.
8. As an operator watching agents, I want new rows, a moved selection, and a Message line to keep painting while a face is stepping, so that the motion never holds the screen over the facts.
9. As the terminal and machine running the plane, I want a face step to cost the paint of one row, not a re-layout of the region's element tree, so that the CPU the tick spends is the glyph and not the screen.
10. As the terminal and machine running the plane, I want a pop tick to paint the box's size and never re-wrap the modal's body text, so that a 120 ms opening costs frame geometry, not text layout.
11. As the terminal and machine running the plane, I want the renderer's frame loop to run only while a frame owner is active, so that a resting plane burns no loop for a face that paints nowhere.
12. As the terminal and machine running the plane, I want the frame's clock, step, and rest to stand in one shared module, so that a bug in the motion settles in one module and not in each screen.
13. As the terminal and machine running the plane, I want the face step to write only the cells the frame changes once the renderer's diff stands (ADR 0145), so that the step is a one-glyph change on the terminal.
14. As the test suite, I want to advance the plane's animation frame by a named amount through one named frame-rig operation, so that the face frame and the pop size stand on the tick I chose, never on wall-clock luck.
15. As the test suite, I want a frame read at the window's open to hold the first frame, so that a snapshot at the open stands the way it does today.
16. As the test suite, I want to drive the pop frame by frame, so that every painted frame from the open to the settled size can be checked, that no frame's content reaches the terminal's edge, and that no wait can miss the window.
17. As the test suite, I want to replace the wall-clock grace over the pop's budget (the 250 ms sleep at the declared minimum) with the named tick to rest, so that the check is deterministic on the local runner and the CI runner alike.
18. As the test suite, I want the production tick source and the test tick source to stand on one port of the frame module, so that a test that drives the module by hand exercises the same clock, the same step, and the same paint handoff that production runs.
19. As the test suite, I want a frame taken after the window ends to hold the state badge or the failure marker and no face, so that the face is the window's and nothing else.
20. As the test suite, I want the gallery to keep painting every shared frame beside its word, so that a reviewer sees the face the shared library owns.
21. As the operator, I want the crash remnant to wear its recovery fact and never the spinner, and its restart to wear the face, so that the face names only a live start.
22. As the test suite, I want the shared gallery's face rows and the paint layer's frames to keep standing under the frame seam, so that a presentation that drifts from the shared face is a test failure, not a reviewer's catch.

## Implementation Decisions

**Module built: the frame module**, in the shared control library beside the shared spinner module and the shared modal chrome module (ADR 0014 puts the spinner face and its written word there; the module that owns their frames belongs with them). The module is deep: two small interfaces hide the liveness rule, the clock step, the rest, and the paint handoff. Today the animation is shallow: the clock stands inside each screen, and the tick path re-runs the screen's whole layout. The deepening moves the clock to the shared module and shortens the tick path to one paint.

**Interface one: the tick port.** Something outside the module hands it a tick, a delta of time. Behind the port stand the two adapters:

- the production adapter: the renderer's animation tick. The module's tick port is wired to the renderer's per-frame callback by the module that owns the renderer - the plane's entry module today, the renderer adapter once ADR 0145 lands - and that wiring holds the renderer live while at least one frame owner is active: it asks the renderer for liveness when the first owner registers and drops it when the last owner leaves. The port's shape does not change between the two owners of the renderer, so this deepening and ADR 0145 are order-safe in either direction. While a tick arrives, the module advances each active owner's clock by the delta and, when the owner's painted fact changes (a new braille frame, a new box size), hands the frame's facts to that owner's paint. Ticks that change no painted fact paint nothing.
- the test adapter: the frame rig's named tick operation, which hands the module a named delta and then paints the frame that follows in the test renderer.

The module hides which source stands: the clock, the step, and the rest are one code path the two adapters drive.

**Interface two: the frame owner.** A surface registers an owner with the module: the structural fact that says the owner is active (the ticket is in its Starting window; the modal is in its opening), and a paint that takes the owner's per-tick fact (the face frame index; the pop scale) and writes it into the renderer's frame. The paint resolves its word and geometry through the shared presentation (the spinner face's text, the modal frame's geometry) and its colors through the shared paint layer (the Theme the environment resolved; the no-color presentation drops the color and keeps the word). React state keeps only the structural fact. Registration stands in a surface effect that lives exactly as long as the owner's window: at the open, the owner applies its opening fact before the first paint (the face stands on its first frame, the box stands on its opening scale, so no frame shows the settled size), and at the close the surface's structural repaint takes the face or the box back to the settled state and the module releases the owner. While an owner stands, the module is the only writer of that owner's per-frame cells, so a structural repaint can never paint a stale frame: a repaint that changes the owner's static facts (the word, the width, the theme) repaints through the same paint.

**First owners: the spinner face and the modal pop.**

- The shared spinner module keeps its frames, its step budget (100 ms), and its face text; its self-driven frame hook leaves the ticket list. The list keeps the structural fact (which visible rows are Starting) in React state, registers one face owner while any visible row wears the face, and the face's row span is painted by the module's tick. One tick source serves many owner clocks: the face's 100 ms step runs on its own clock beside any other owner's clock, and the list can hold several starting rows with one face owner.
- The shared modal chrome module keeps the pop's budget (120 ms), its opening scale, and its easing; its self-driven scale hook leaves the Decision modal and the Live view. The modal registers one pop owner for its opening. During the opening the module paints the intermediate box size into the modal's frame, and the modal's body text is wrapped once, at the settled content width: the intermediate frames show the body clipped to the box, and the settled frame shows it exactly as today. The per-tick body re-wrap (the detail body's wrap, the live body's facts) leaves the tick path and runs only when the body's content or structure truly changes.

**Decided against: the renderer's built-in animation engine.** The production renderer ships an animation engine (timelines that interpolate renderable properties, with the engine holding the renderer's liveness while a timeline plays). The module does not take it: the plane's frame facts are named values (a frame index, a scale on the plane's own easing) painted through the plane's own presentation, not interpolated renderable properties. The engine and the module stand on the same seam anyway: the renderer's per-frame tick. The module takes the tick directly and owns its liveness, so the plane's motion never depends on the engine's interpolation model, and the test renderer (which never runs the engine's tick) needs no engine of its own.

**Unchanged.** The face's frames, step, and word; the pop's budget, opening scale, and easing; the module that creates the renderer (the plane's entry module today, the renderer adapter once ADR 0145 lands) and the full-repaint callback it installs on every frame (it stands until the paint-seam work retires it); every key, control, and color role. The deepening moves where the tick stands, not what the tick paints.

**Locality and leverage.** The clock, the step, the rest, the liveness rule, and the paint handoff settle in the one shared module: a bug in the motion (a step that skips a frame, a pop that rests short, a face that survives its window) is found and fixed in that module, and the library's automated check rejects a screen that keeps or regrows its own per-frame timer. One tick port and one owner interface serve the face and the pop now and the next animated control later: each new owner is a registration, not a mechanism.

## Testing Decisions

A good test here drives the real application flow through the shared frame rig and asserts the painted frame only: what row shows what face, what size the box wears, whether the frame is settled, and whether the screen's edge is clean. No test reaches for the clock, the callback, or the renderable; no test waits on a wall-clock window for the animation's budget to run out.

Modules tested through the seam, and their prior art:

- **The spinner face through the ticket list**: `test/starting-face.test.ts` already walks the real flow (the manual handoff, the failed start, the auto handoff, the workflow route, the restart of a crash remnant, a turn that settles under a handed-off ticket) and checks the written word beside any of the shared frames, with the failure marker beating the face and the recovery fact never wearing the spinner. It keeps its scope and gains the named tick: the check on the face frame moves from "any shared frame" to "the frame the tick I sent stands on", and the frame read at the open still holds the first frame.
- **The modal pop**: `test/decision-modal.test.ts` owns the pop-in suite ("no content ever reaches the terminal's edge while the box grows", the settled-frame brightness check, the scrollbar pinned at the settled size, the nested border at the declared minimum). The frame-stream waits keep their rule (wait on the stream, never on a wall-clock window) and the 250 ms wall-clock grace at the declared minimum becomes the named tick to rest. `test/live-view.test.ts` keeps its "the pop-in settles before the geometry is measured" checks, now settled by the named tick.
- **The shared presentation and the paint layer**: `test/shared-gallery.test.ts` (the gallery paints the shared face's frames beside their words) and `test/theme-frame.test.ts` (the paint layer's frame under the resolved Theme and the no-color presentation) keep standing under the seam unchanged: the presentation the module hands to the paint is the presentation the gallery and the paint layer already check.
- **The rig itself**: `test/frame-rig-architecture.test.ts` keeps policing the owned surfaces through the rig's named controls, and it gains the one new named operation of this change to the rig's expected surface. `scripts/walk-frame-rig-counts.ts` keeps policing the rig's export surface: the new operation grows the count, and the rule is that it grows, never falls.

The test-side adapter is the second standing behind the tick port: the production renderer tick and the rig's named tick drive one clock and one paint handoff, so a green frame test says the module's tick path is the path production runs.

## Out of Scope

- **The paint-seam work that restores the renderer's diff (ADR 0145)** is separate. This deepening stands on the renderer as it stands: the full-repaint callback the owner of the renderer installs on every frame stays until that work retires it, and it makes no claim about the bytes a frame writes.
- **The face's presentation and the pop's presentation are unchanged**: frames, step, word, budget, opening scale, easing. The no-color presentation keeps dropping only the color.
- **No other animated control joins this round.** The face and the pop are the first owners; a later motion registers on the owner interface without a new mechanism.
- **The renderer's built-in animation engine is not adopted** (decided above), and the owner of the renderer keeps creating it the way it does.
- **The open items ADR 0024 and the shared-controls verification record name** (the screen-reader path, the inherited-theme contrast) are untouched by this change.

**How this deepening behaves before and after ADR 0145's repaint policy.** Without the policy: each tick frame the module paints is a full-screen rewrite under the full-repaint callback the owner of the renderer installs, and the live frame loop repaints the screen at the loop's rate (the renderer's 30 fps target) for as long as any owner is active. So this deepening alone saves CPU (no repaint, no element-tree re-layout, no body re-wrap per tick) but not terminal bytes, and during a long Starting window the byte rate can stand above today's ten-per-second tick rate, because the live loop outruns the face's 100 ms step. With the policy: a frame that changes no cell writes no bytes, the live loop's idle frames are free, and the face step becomes a one-glyph change on the terminal. The two are order-safe in either direction: landing this deepening before ADR 0145 is correct on the full-repaint renderer, and the renderer adapter landing first is correct on the repaint-driven clock; this deepening becomes the stronger play once ADR 0145 lands, because the live loop then costs nothing while it waits for the next step.

## Further Notes

- **The dependency on ADR 0145, precisely**: without the renderer adapter's repaint policy, each animation tick still forces a full-screen rewrite, so this deepening alone saves CPU (no root commit, no element-tree re-layout, no body re-wrap) but not terminal bytes; with the policy the tick becomes a one-glyph change. The live-loop rate note above (30 fps under the full-repaint callback while an owner is active) is the one place this deepening alone raises the byte rate over today's, and it is the exact cost ADR 0145 removes.
- **Liveness is the module's, ref-counted**: ask on the first owner, drop on the last. A plane with no face stepping and no modal opening holds no liveness and keeps its one-frame-per-commit economy exactly as it does today.
- **The structural repaint and the frame tick share one writer per owner cell** (the owner's paint). That is what keeps a repaint from painting a stale frame, and it is the rule the automated check enforces when it rejects a screen-local frame timer.
- **Glossary and record updates land with the change**: the Spinner entry's "drives its own frames the way the Decision modal's pop-in drives its own" line is rewritten to name the frame module as the driver, and the verification record names the new rig operation and the suites that exercise it.
