# The homepage hero is a real herdr capture

Status: accepted.

The documentation homepage shows one hero image of the control plane at work.
The six operation screenshots already render the control plane in a plain
terminal from a deterministic PTY fixture, and a drift test guards them. The
homepage should show the control plane in its real container, a herdr
workspace, so a first visitor sees the product the way an operator runs it.

## Decision

The hero is generated by a script, `npm run hero`. The script drives a real,
isolated herdr: a fresh server in a temporary directory with its own socket,
home, and config. It never touches the operator's live herdr session. The
script makes two workspaces, the way a real run stands: the control plane
runs full width in its own workspace over the same deterministic fixture the
operation screenshots use, and the running ticket's handoff environment is
its own workspace on its own checkout, unfocused. The shot shows only the
plane; the agent is a fact of herdr's sidebar, not a pane beside the plane.
The script selects the running ticket in the control plane, so the Detail
pane shows the ticket the agent works, and it reports the agent's pane to
herdr as a working agent, so the sidebar carries the agent's workspace and
the running state the ticket's row reads. The isolated herdr stands on the
theme the operator's herdr stands on, so the shot paints the theme the
operator runs: the theme name is pinned in the screenshot fixture's script,
shared with this one, because a capture must stand on a theme every machine
resolves to the same bytes. An attached herdr client renders the plane's
workspace, and the script captures the client's screen with the shared ANSI
renderer into `docs/public/hero.png`.

The hero is refreshed by hand. It is not in the drift test.

## Considered Options

- Draw a mock herdr chrome around the fixture. This was rejected: a mock
  drifts from the real herdr, and it costs a second renderer to keep.
- Put the hero in the drift test. This was rejected: herdr owns the chrome
  (the sidebar, the pane borders, the tab bar), and the chrome changes when
  herdr changes. A drift test would fail on every herdr upgrade for a reason
  outside this project.

## Consequences

- The control plane pane in the hero is deterministic: it comes from the same
  fixture as the operation screenshots, and its `gh` and `herdr` lookups resolve
  to the fixture's stubs. The agent's workspace is a stub: its pane holds a
  static process, and its state comes from the script's report. Only the herdr
  chrome varies, and it varies with herdr.
- The hero is a manual artifact. Refresh it when herdr changes or when the
  main view changes in a way the homepage should reflect.
- The theme is a pinned input, not a live read: when the operator's herdr
  changes theme, update `HERDR_THEME_NAME` in
  `scripts/screenshot-fixture.ts` and re-run both `npm run screenshots` and
  `npm run hero`, so the shot and the operation screenshots stay on one theme.
- The capture is isolated. A failed or interrupted run leaves no herdr state
  outside the temporary directory, and the operator's session is never read or
  written.
- The image lives in the site's static asset directory, `docs/public/`, and
  the homepage references it by site path.
